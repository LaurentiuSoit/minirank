Plan

Preparation

Before starting the implementation of the project, I first held a brainstorming session with Claude to clarify the requirements and scope of the project. We discussed the features, common pitfalls, things to look out for, which technologies would best suit the project, which free models to pick based on the restrictions that were imposed and other topics to ensure the development process went smoothly.

Using the information gathered in the brainstorming and other personal preferences/details, i manually wrote an AGENTS.md file to establish a comprehensive ruleset for the agent to follow. This file contained context of the application, things to look out for (like security concerns), things to do, things to avoid, details about my prefered working style etc.

I attribute a great deal of the project's success to the AGENTS.md file, as it represented a great base and guardrail for the agent, ensuring that the generated code was aligned with my expectations and requirements. It also helped to reduce the number of mistakes made by the agent, as it provided clear guidance on what to do and what to avoid, also ensuring that it can correct mistakes by itself, thus reducing developer intervention and time spent reviewing.

Stack & scope decisions

  • Backend: plain PHP (no framework), the brief specifically flags that a large framework scaffold works against a small-context free model, so a thin, explicit codebase was chosen deliberately.
  • Database: SQLite, per M7's recommendation, zero setup, trivial to seed, easy for the grader to run with a single php -S command.
  • Frontend: server-rendered HTML/CSS with a small amount of vanilla JS for the AJAX refresh (M3) and the chart (S1).
  • Models: the OpenCode Zen model i chose was Laguna S 2.1, as the suggested DeepSeek model did not function. The first fallback, the free tier Google Flash model, Gemini 3.7 Flash, also proved unusable. The "emergency lane" model from OpenRouter, Laguna XS 2.1, was my 2nd fallback.

Key decisions

  • Keep it simple. The main idea behind the implementation was to have an application that is light, uses basic and easy to understand features and spends the least amount of tokens.
  • Guardrail from the get-go. I decided to use an AGENTS.md file from the very beginning, in an attempt to reduce agent mistakes and omissions, thus reducing time and tokens spent on improving the app.
  • Heavy planning. Each feature set (Mandatory and Stretch goals) included a great deal of planning, both for the set as a whole, creating a general overview of the implementation process and order, as well as distinct, feature specific plans, where details were discussed, ambiguities were cleared up and important decisions were made.

What I'd change in hindsight

In hindsight, one important aspect I would change would be the session handling for the tasks. I could have used fewer sessions, merging smaller features into one session, thus reducing costs for regaining context for every single feature.

Prompts & Fixes

Three real prompts that mattered, including one that failed, with the concrete mistakes the AI made and how they were caught.

Prompt 1
"Make a plan for implementing the auth + csrf step of the stretch_goals_plan.md"

What happened

Careful ordering decision (auth check before CSRF check on POSTs, for a friendlier redirect instead of a raw 400). Caught that the AJAX refresh button is a fetch() call, not a form, so it needed a tag to carry the CSRF token, not just a hidden form field. Explicitly avoided running the password field through the generic validateString() trim helper, reasoning that trimming a password is a subtle bug. Flagged 5 separate open design questions (Q1-Q5) instead of guessing.

Mistakes and fixes

The agent proposed an implementation that affected 10 files, without mentioning a split of tasks. I let it slide due to the scope of the feature and concerns regarding token usage. During testing, the agent hung up and I had to awaken it. It also changed the port of the server it started from 8000 to 8765 without asking or explaining why.

Prompt 2: the one that failed
"Implement the features described in DB_SEED_PLAN.md. Other relevant information for the application can be found in the md files mentioned at the start."

What went wrong

On the first prompt, the AI spent its entire turn silently re-litigating trivial placement questions (e.g. whether date_default_timezone_set('UTC') belongs in db.php or seed.php) without calling a single tool or writing any file. It went completely idle.

How I caught it and recovered

I had to send a literal "are you still working?" before it responded: "I haven't actually written any files yet — I've only read the planning documents." Only then did it produce src/db.php and seed.php.

Prompt 3
"Based on the Stretch Goals Plan, make a plan for step 1 of the Implementation Order" "1. Optiona A
2. include it
Write this plan in an md file, then implement it"

What happened

Before building, it flagged upfront that docker-php-ext-install pdo_sqlite might fail without libsqlite3-dev. It then actually did fail during docker build and instead of silently patching, it said "As I flagged in the plan, pdo_sqlite compilation needs...", applied its pre-documented fallback, and went back and corrected the plan file to match reality. Good real "predicted failure -> it happened -> proper recovery" story. Also correctly kept DB seeding CLI-only.

Mistakes and fixes

Despite AGENTS.md mentioning no git commits in the plan file, it did inlucde one.

Retrospective

What I'd do differently

I would mainly try and shorten the number of sessions, as I feel like a good portion of tokens and time were spent on the agent regaining context of the application, when multiple small features could've fit in one session.
